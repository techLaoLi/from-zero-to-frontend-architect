# AI 生成的技术债长什么样？怎么提前还

**AI 生成的技术债，是在测试仍绿、功能仍能演示的情况下，以机器速度堆积的重复实现、模块混乱和约定漂移；它不会自己报警，必须靠定期一致性检查提前还。**

传统技术债常伴随疼痛：编译难过、缺陷扎堆、发布变慢。AI 债更安静——每笔变更局部正确，合在一起却把仓库变成「很多正确的碎片」。本文认三种典型债、解释为什么绿灯不可靠、以及怎么在烂透前做一致性回收。

## 重复实现、模块混乱、约定漂移三种典型债

AI 债有稳定外观，审查时按类型识别比按文件名识别更有效。

| 类型 | 表现 | 怎么认 | 长期代价 |
|---|---|---|---|
| 重复实现 | 同一能力出现第二套工具函数、第二套请求封装、第二套鉴权判断 | 新文件「很完整」，却不调用已有入口 | 修 bug 要打两处；行为渐渐分叉 |
| 模块混乱 | 边界被临时需要打穿：UI 直连存储、共享层依赖业务细节 | import 方向违反原分层；「先打通再说」的跨层调用 | 改一处抖全身；无法独立测试 |
| 约定漂移 | 命名、错误处理、目录、日志、API 形状与仓库规范不一致 | 单看新代码自成风格，和邻文件并排就刺眼 | 规则失效；后人（和下一轮 AI）无所适从 |

三种债常结伴出现：重复实现带来第二套约定，第二套约定再诱使下一轮 Agent 继续漂移。根因通常不是模型「不会写」，而是上下文里缺「已有做法」或任务允许它就地发明。

决策含义：还债优先级按「分叉速度」排。重复的鉴权与支付路径优先于重复的格式化工具；约定漂移若已影响 Agent 后续生成质量，也要提前排期——它会放大以后所有债。

## 为什么它不会自己暴露：测试还是绿的

测试绿灯证明的是「已声明行为没破」，不证明「实现只有一份」「边界还在」「约定还被遵守」。

| 仍绿的原因 | 实际情况 |
|---|---|
| 新实现配了新测试 | 两套实现各自对各自的断言负责，互不打架 |
| 旧测试只钉行为，不钉结构 | 平行模块不在旧断言视野里 |
| 类型与 lint 过了 | 风格局部自洽，跨仓库一致性不在规则里 |
| 演示路径只走新代码 | 旧路径腐烂但无人调用，直到某次切换 |

所以「绿」会给出错误安全感：团队以为质量在线，其实只是缺陷被推迟到「需要统一行为」或「新人/Agent 读不懂该用哪套」的那一天。那一天的成本，按机器堆积的周数指数上升。

决策规则：合并门禁里的绿，只关闭「行为回归」这一项风险；结构风险要另设检查，不能从 CI 绿推导出来。把「测试绿 = 无技术债」写进团队口头禅，等于关闭雷达。

## 定期做一致性检查，不等到烂透再重构

提前还债的手段是高频、小规模的一致性检查，不是年度大重构。大重构正好是 AI 最容易一次生成上千行、再制造新债的场景。

可落地的节奏：

| 动作 | 频率建议 | 产出 |
|---|---|---|
| 重复实现扫描 | 每迭代或每两周 | 同名能力、相似函数、双入口列表 |
| 分层与依赖方向检查 | 跟 CI 或每周 | 违规 import 报告 |
| 约定抽样对照 | 每周 | 与 AGENTS.md / 示例代码的差异清单 |
| 小步合并 | 发现即开任务 | 每次只删一套重复或只修一层边界 |

原则：

1. **发现即立还债任务，限体积。** 一次只收一条重复实现或一个方向的依赖违规；禁止「顺便大扫除」。
2. **用测试锁住去重后的唯一入口。** 删掉平行实现前，先让唯一入口承担全部相关断言。
3. **把一致性规则自动化。** 能写成 lint、架构测试、依赖图检查的，不要靠节目录查。人的定期检查只覆盖还自动化不了的语义判断。
4. **生成任务默认禁止新开平行抽象。** 规格里写死：先搜索已有模块；找不到再申请新建，并说明为什么旧的不够。

等「烂透」再重构，你会同时面对行为风险和体积风险——恰恰是审查最审不动的组合。在仍然绿、仍然小的时候还，是唯一划算的窗口。

## 要点总结：技术债在机器速度上累积

1. AI 债的典型形态是重复实现、模块混乱、约定漂移，常在功能正确时出现。
2. 测试绿不报告结构问题；绿只是行为尺子，不是架构尺子。
3. 用高频小规模一致性检查提前还，避免一次大爆炸重构。
4. 决策边界：生成越快，越要显式安排还债带宽；不安排，债按机器时钟计息。
