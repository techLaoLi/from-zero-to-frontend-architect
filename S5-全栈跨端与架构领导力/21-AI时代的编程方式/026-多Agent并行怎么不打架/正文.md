# 多个 Agent 并行做同一个需求，怎么避免互相打架

**多 Agent 并行是把同一需求拆成可隔离的子任务，让多个 Agent 在各自工作树上推进，再用独立的合并裁决把结果收成一份可审查变更；省的是等待时间，付的是隔离与合并成本。**

本文只谈并行不打架的分工与边界。初级工程师怎么带、团队规范写哪几条，不在这里展开。

## 分支隔离：每个 Agent 一个工作树

并行打架的根因是共享工作区：两个 Agent 同时改同一批文件，后写覆盖先写，或半成品互相污染上下文。

硬规则只有一条：一个 Agent 对应一份隔离的工作树（或等价隔离环境），不共用脏的工作目录。

| 做法 | 作用 | 不做什么 |
|---|---|---|
| 每 Agent 一工作树 / 一分支 | 文件变更互不覆盖 | 不解决需求拆分错误 |
| 任务按模块或接口切分 | 降低改同一文件的概率 | 不消灭最终合并冲突 |
| 共享只读基线（规格、接口） | 大家对着同一份事实 | 不把未合并 diff 当事实 |

隔离解决的是「执行期踩踏」。它不自动保证子任务边界正确。若两个任务都要改同一个核心模块，并行本身就不该开——先串行锁接口，再并行写实现。

可当场检查：每个 Agent 的写入路径是否落在自己的工作树？有没有人在共享 checkout 里并行写？

## 用一个额外的 Agent 做合并裁决

并行产出多份 diff 之后，需要一个明确的合并角色，不能靠「谁先推完谁说了算」。

合并裁决 Agent（或人扮演同一角色）只做三件事：对齐规格、解决冲突、验证整体验收。它不重新发明需求。

| 步骤 | 裁决者做什么 | 产出 |
|---|---|---|
| 对齐 | 对照规格核对每份 diff 的目标与非目标 | 超出范围的改动打回或删掉 |
| 冲突 | 同一文件的分歧按设计文档取舍，不按生成先后 | 一份无冲突的候选合并 |
| 验证 | 跑集成测试、类型检查、约定扫描 | 过关则交人终审；不过则定点打回 |

裁决 Agent 需要比执行 Agent 更窄的权限叙事：它读全部候选变更和规格，但默认不大规模重写业务逻辑。大面积重写等于否定并行分工，应回到任务拆分。

人仍然守终审：合并 Agent 解决的是机械冲突和明显越界；跨模块的取舍、对外行为变更，仍由人签字。

## 什么时候并行才划算

并行不是默认加速键。只有隔离成本 + 合并成本 < 串行等待成本时，才划算。

| 条件 | 更适合并行 | 更适合串行 |
|---|---|---|
| 子任务文件集合 | 几乎不相交 | 大量重叠 |
| 接口稳定性 | 接口已锁死 | 接口还在谈 |
| 验收方式 | 各有独立测试，再加一层集成 | 只能靠手工点一整条链路 |
| 团队带宽 | 有人（或 Agent）专职合并裁决 | 没人收口，靠碰运气 rebase |

经验边界：两个以上 Agent 改同一核心模块、或规格仍在变，并行会把冲突从「执行期」推迟到「合并期」，总时间往往更长。先把需求拆到「可独立验收的切片」，再谈并行。

决策句：能画出互不重叠的写入集合，并指定合并裁决者，才开并行；画不出来，就串行。

## 要点总结：并行省时间，合并要付账

1. 每个 Agent 一份工作树，隔离写路径，避免共享脏目录。
2. 另设合并裁决角色：对齐规格、解冲突、跑整体验收，再交人终审。
3. 文件重叠大、接口未锁、无人收口时，并行不划算。
4. 并行省的是等待；合并、冲突和终审是必须预留的账。
