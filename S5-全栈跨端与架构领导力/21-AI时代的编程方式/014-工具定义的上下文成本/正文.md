# MCP 工具定义为什么吃掉这么多上下文

**工具定义是 Agent 启动时就要塞进上下文的「菜单」：每个可调用工具的名称、参数结构和用途说明。菜单越长，留给任务材料的预算越少——这笔开销在你还没提问之前就已经扣掉了。**

MCP（Model Context Protocol）把外部系统接进 Agent 时，工具定义往往常驻窗口。本文讲清楚这笔成本从哪来、怎么缓、以及「装几个够用」该怎么拍板。

## 工具定义为什么常驻消耗上下文

模型要先知道「能调什么」，才会在规划步骤时考虑用工具。因此工具定义通常不能等用到了再偷偷出现——至少在当前主流 Agent 形态里，一批工具的 schema 会作为可见能力清单提前进入上下文。

和「读一个业务文件」不同，工具定义有三个贵的地方：

| 贵在哪 | 原因 |
|---|---|
| 常驻 | 多数情况下整轮会话都带着，不是读完就丢 |
| 按工具累加 | 每多一个工具，就多一段名字 + 参数 + 说明 |
| 与任务无关也占坑 | 今天只改前端组件，数据库迁移工具的定义仍可能在窗口里 |

接多个 MCP 服务器、每个服务器再暴露一批工具时，定义合计吃掉数万 token 并不罕见。这时你还没 `@` 任何业务文件，预算已经被「能力清单」先花掉一截。

决策含义很直接：装 MCP 不是免费插件，是在买能力的同时持续付上下文税。税太高，模型看见规格和关键代码的机会就变差。

## 按需发现和工具搜索怎么缓解

常驻全量菜单不是唯一做法。工程上常见的缓解方向是「先看见目录，再展开详情」。

| 策略 | 做法 | 省什么 |
|---|---|---|
| 按需发现 | 先暴露少量元信息或分组，真正调用前再拉取完整 schema | 避免所有参数说明一上来全进窗口 |
| 工具搜索 | 用检索从大量工具里选出候选，再只加载候选定义 | 把「全量常驻」变成「相关子集常驻」 |
| 会话级启用 | 按项目或任务开关 MCP，而不是全局永远全开 | 砍掉本任务用不到的整组工具 |

这些策略不改变「用工具前要有定义」这件事，只改变「什么时候、以多大范围」把定义推进窗口。缓解的是峰值和常态占用，不是取消工具本身的成本。

落地时有一条边界：如果搜索和发现本身也要靠另一套庞大工具来完成，要算清净收益。目标是降低无关定义的常驻比例，而不是再叠一层更重的间接层。

## 装几个 MCP 服务器才够用

够用不是「能力覆盖面最大」，是「当前工作流高频路径刚好覆盖，且上下文税可接受」。

拍板时用这张表，而不是凭「以后可能用到」：

| 问题 | 倾向少装 | 倾向保留 |
|---|---|---|
| 本周真实任务有没有反复打到这个系统？ | 没有 | 几乎每天都打 |
| 不用 MCP，用脚本 / CLI / 已有 CI 能否同样闭环？ | 能 | 不能，或缺权限/交互 |
| 这组工具定义大概有多胖？ | 工具多、说明长 | 工具少、schema 短 |
| 关掉它之后，失败模式是否可接受？ | 可接受（多两步人工） | 不可接受（阻塞主路径） |

实践上的默认策略：

1. **默认少装。** 先保证读写仓库、跑测试、查本仓文档这些主路径。
2. **按项目启用。** 前端仓不必常挂运维面板；活动页不必常挂数据仓库。
3. **复盘再加。** 连续多次因缺少某连接而失败，再装对应 MCP，并观察窗口占用是否可接受。

「装全了最省心」在 AI 编程里通常是错的。省心的是主路径顺，不是菜单最长。

## 要点总结：少装是最省的办法

1. 工具定义是常驻菜单：名字、参数、说明都进上下文，和本轮任务是否用到无关。
2. 多 MCP、多工具时，定义本身就可以吃掉数万 token 量级的预算，挤压规格和代码。
3. 按需发现、工具搜索、会话级开关能缓解，但治本仍是减少常驻工具面。
4. 选型标准是高频真实路径，不是能力收藏；少装是对上下文预算最直接的保护。
