# 上下文窗口是什么？为什么它决定了 AI 的表现

**上下文窗口是大模型在一次推理里能同时看见的全部输入：系统规则、工具定义、对话历史、你引用的文件、命令输出，以及当前这一轮提示。超出窗口的内容，模型等于没看见。**

窗口大小决定了「最多能塞多少」。真正决定表现的，是这些位置里装了什么、谁先占坑。本文把上下文当成预算来看，而不是越大越好的仓库。

## 上下文的定义：模型一次能看到的全部信息

上下文不是「仓库里有什么」，是「这一轮请求里模型实际读到了什么」。

一次 Agent 调用里，常见组成大致是这些块：

| 组成 | 典型内容 | 是否常驻 |
|---|---|---|
| 系统与规则 | 产品内置指令、`AGENTS.md`、项目规则 | 常驻或按会话加载 |
| 工具定义 | 每个可调用工具的名称、参数、说明 | 常驻（尤其 MCP） |
| 对话历史 | 你和模型之前的话、中间结论 | 随会话增长 |
| 任务材料 | 你 @ 的文件、自动读入的片段、报错日志 | 按任务增减 |
| 当前提示 | 这一轮你真正要它做的事 | 每轮都有 |

模型的「记忆」在窗口里，不在硬盘里。文件写进仓库不等于它知道；只有被读进本轮上下文，才进入决策。

所以架构判断要换一句问法：不是「模型支持多长」，而是「这一轮预算里，任务相关信息占了多少、噪音占了多少」。

## 为什么长上下文不等于好上下文

窗口变长，解决的是容量上限，不自动解决相关性。

长上下文常见的三个误区：

| 误区 | 实际后果 |
|---|---|
| 整仓塞进去最省事 | 相关信号被淹没，模型更容易抓住相邻但错误的片段 |
| 历史越留越全越稳妥 | 旧任务的假设、半成品方案继续污染新任务 |
| 窗口够大就不用管预算 | 工具定义和无关文件先占坑，真正关键的规格反而挤到后面 |

更长的窗口更像更大的桌面：桌面大了，你可以摊更多图纸；也可以把上周的外卖单、过期合同一起摊上去。决策质量取决于你留下什么，不取决于桌面面积。

还有一层工程现实：窗口用满之后，系统往往会摘要、截断或丢掉更早的内容。你以为还在「记得」，其实关键约束已经被挤掉了。长上下文给了容错空间，没有取消「该进什么、不该进什么」的决策。

## 上下文被什么挤满：工具定义、历史、文件内容

挤满窗口的通常不是「这一轮最关键的那几段代码」，而是三类常驻或半常驻开销。

**第一，工具定义。** 每个工具要把名字、参数 schema、用途说明放进上下文，模型才知道能调什么。接多个 MCP 服务器、每个服务器再挂一批工具时，定义本身就可以常驻吃掉大量 token——数量级可以到数万，还没开始读你的业务代码。下一篇专门拆这笔账。

**第二，对话历史。** 同一会话里改过三个需求、试过两种方案、贴过两段失败日志，这些都会继续占用位置。对模型来说，它们仍是「可见事实」，哪怕你心里已经换题了。

**第三，文件内容。** 一次 `@` 整个目录、或让 Agent 「先把相关文件都读一遍」，很容易把半相关模块、生成物、锁文件一起灌进来。读文件是必要能力；无差别灌文件是预算浪费。

三类开销的决策含义不同：

| 开销来源 | 你能控什么 |
|---|---|
| 工具定义 | 少装、按需发现、别为「以后可能用」预挂一堆 |
| 对话历史 | 任务边界清就新开会话，重要结论落到文件 |
| 文件内容 | 引用具体路径和片段，先规格后广搜 |

窗口是共享池。工具定义先扣一笔固定成本，历史再扣一笔沉没成本，留给「当前任务证据」的空间就被压缩了。表现变差时，先查预算结构，再怪模型不够聪明。

## 要点总结：上下文是预算，不是仓库

1. 上下文窗口是一次推理里模型能看见的全部输入；仓库里有、窗口里没有，等于不存在。
2. 更长的窗口提高容量上限，不自动提高相关性；噪音和信号一起变多。
3. 常见挤占来自工具定义、对话历史、大段文件内容，而不是「真正要命的那几行」。
4. 架构动作是分配预算：常驻开销能砍就砍，任务材料按需进入，过期假设及时清场。
