# 怎么把需求写成 AI 能执行的规格

**可执行的规格是一份把需求拆成五块硬信息的文档：要做什么、不做什么、约束、验收标准、边界条件；每一块都写到模型读完后不需要再猜，并且验收条件能直接变成测试或检查命令。**

上一篇说了规格是唯一事实来源。这一篇落到写法：缺哪一块，AI 就会用默认假设填哪一块。目标不是写长，而是写到可判定。

## 规格的五块：要做什么、不做什么、约束、验收、边界

一份够用的规格，至少覆盖这五块。少一块，缺口就会变成自由发挥。

| 块 | 写什么 | 写糊了会发生什么 |
|---|---|---|
| 要做什么 | 本次要交付的行为或结果 | 模型扩大范围，顺手做「相关功能」 |
| 不做什么 | 明确排除的目标和非目标 | 模型按「完整产品」补全你没要的部分 |
| 约束 | 技术栈、目录、依赖、安全、兼容性 | 模型换库、换目录、换实现风格 |
| 验收 | 怎样算做完，最好能跑 | 做完无法自证，只能靠人肉读 diff |
| 边界 | 允许改哪些文件/模块，禁止碰哪些 | 一次改十个文件，审查成本爆炸 |

五块里，「要做什么」最好写，也最容易写虚。「加一个记住我」不够；要写成：登录成功后可选持久化会话，刷新页面仍保持登录，直到用户退出或过期。动词、对象、结果都在句里。

「约束」和「边界」常被混在一起。约束回答「用什么规矩做」；边界回答「许改哪里」。一个管方法，一个管范围。

写规格时按这个顺序最稳：先划不做什么和边界，再写要做什么，最后落验收。反过来先写愿望清单，非目标和边界往往会被挤没。

## 什么叫可验收：能写成测试的才算

可验收不是「产品经理点头」，而是「存在一种客观办法证明它成立或失败」。

对 AI 编程来说，最硬的验收是能写成自动化检查的条件：

| 验收写法 | 是否可验收 | 原因 |
|---|---|---|
| 「体验要流畅」 | 否 | 无法客观判定 |
| 「登录后刷新仍保持登录」 | 是 | 可写成端到端或集成测试 |
| 「不要影响现有用户」 | 弱 | 范围不清；应改成具体回归范围 |
| 「`npm test` 全绿，且新增用例覆盖过期清理」 | 是 | 命令和范围都明确 |

一条经验法则：如果你不能在规格里写出「失败时会看到什么」，这条验收就还没写完。模型无法对模糊句子闭环；它只会生成一段看起来像做完了的代码。

人仍然要守两类验不了自动化的东西：产品判断（该不该做）和架构一致性（该不该这样拆）。但这两类也不该用形容词搪塞，而要写成可讨论的取舍，留给设计文档去锁。

## 显式写非目标，为什么不能省

非目标是规格里性价比最高的一段，也是最常被省掉的一段。

AI 的默认倾向是「做得更完整」。你说做搜索，它可能补筛选、补排序、补空态插画、补管理后台。每一项单独看都合理，合在一起就是范围失控。

显式写非目标，等于提前关掉这些岔路：

| 需求 | 非目标示例 |
|---|---|
| 登录页「记住我」 | 不做第三方登录；不改密码策略；不做多设备会话管理 |
| 列表加分页 | 不做无限滚动；不改排序规则；不引入新的状态库 |
| 导出 CSV | 不做 Excel；不做定时导出；不改权限模型 |

非目标有三个作用：压缩搜索空间、降低误改概率、给审查提供否决依据。审查时看到「规格写了不做 X，diff 里出现了 X」，可以直接打回，不必争论好不好。

省掉非目标的常见借口是「太明显了」。对你明显，对模型不是。模型没有你们团队的历史包袱，它只看到当前提示和仓库里的邻近代码。

## 要点总结：先写清楚不做的事

1. 规格至少五块：要做什么、不做什么、约束、验收、边界；缺一块就留一个填空题给模型。
2. 可验收的标准是能写成测试或检查命令；形容词不是验收。
3. 非目标必须显式写，用来关掉「顺便做完整」的默认倾向。
4. 边界在这里：先写清楚不做的事，再写要做的事，规格才压得住执行。
