# 为什么 AI 写的代码必须过自动化检查

**AI 生成的代码必须先过自动化检查，再进入人工审查：机器负责拦截可判定的错误，人只保留不可自动化的判断——架构取舍、安全语义、产品边界。**

生成速度一旦超过阅读速度，靠人眼扫 diff 会系统性漏检。自动化检查不是「有了更好」，而是「没有就不能把 AI 产出当团队资产」。本文讲清为什么人工扛不住、四类检查各管什么、以及为什么要把生成结果默认当成不可信输入。

## 人工审查扛不住生成速度

审查成本大致随变更行数和文件数上升；生成成本在 Agent 模式下接近常数。两边速率一错位，团队会出现一种假繁荣：PR 很多、评论很少、线上问题却在涨。

人审失败通常不是态度问题，是带宽问题：

| 现象 | 原因 | 后果 |
|---|---|---|
| 只看文件名和 PR 描述 | diff 太长，没法逐行 | 重复实现、边界破坏混进主干 |
| 只盯业务逻辑 | 类型、风格、依赖漏洞没精力看 | 低级错误消耗线上和返工 |
| 「先合再说，有问题再改」 | 合并压力大于审查压力 | 技术债按机器速度堆积 |

决策很直接：凡是能写成确定性规则的检查，不准占用人工审查配额。人的时间只花在「规则写不出来、或写出来会误伤」的地方。自动化检查是审查的前置门禁，不是审查的可选项。

一个可操作的阈值：Agent 交 diff 时，CI 未绿，审查者有权直接拒绝阅读。读红的 diff，等于用昂贵带宽做机器该做的事。

## 类型检查、lint、测试、扫描各管什么

四类检查解决四类不同的「不可信」。混为一谈，就会出现「测试绿了所以安全」这种错误推理。

| 检查 | 主要抓住什么 | 抓不住什么 |
|---|---|---|
| 类型检查 | 签名不匹配、空值路径、错误的属性访问 | 业务对不对、架构该不该 |
| lint / 格式与约定 | 风格、禁用 API、简单坏味道、部分约定 | 深度设计问题、跨模块语义 |
| 测试 | 已声明行为是否仍成立 | 没写进断言的行为、性能、真实安全攻击面 |
| 安全 / 依赖扫描 | 已知漏洞、密钥形态、危险调用模式 | 业务层逻辑漏洞、错误的授权模型 |

落地时的决策顺序建议固定为流水线，而不是「哪样方便跑哪样」：

1. **类型检查**：不过就停。类型不过的代码，讨论业务无意义。
2. **lint**：把约定从口头变成可失败的规则。能 lint 的约定，不要写进审查清单靠人盯。
3. **测试**：单元、集成、关键路径按仓库既有分层跑。没有覆盖本次行为的测试，视为未完成。
4. **扫描**：依赖漏洞和密钥泄漏用工具扫；扫到的高危默认阻断合并。

这四层是互补，不是替代。关掉其中一层，漏掉的那类错误会重新砸进人审或线上。团队要做的决策是「每层失败时的门禁级别」（警告还是阻断），不是「要不要做」。

对 AI 产出，默认全部阻断级：生成成本低，放行错误的成本高。只有明确的例外（例如实验分支、文档-only 变更）才降级。

## 把 AI 生成的代码当成不可信输入

安全工程里有一条老原则：外部输入不可信，必须校验。AI 的输出在工程上更接近外部输入，而不是同事提交。

原因有三条，每条都指向同一决策——默认不信任，用管道过滤：

| 原因 | 含义 | 对应措施 |
|---|---|---|
| 来源不可控 | 同一提示词，不同会话、不同模型，输出分布不同 | 用检查锁行为，不靠「这次模型看起来靠谱」 |
| 表面像内部代码 | 命名、结构、注释都像本仓库风格 | 更要靠机器规则，防止「像」替代「对」 |
| 失败模式特殊 | 会完整实现错误假设，而不是留空白等你填 | 测试与扫描必须覆盖假设边界 |

「不可信」不是道德指控，是工程分级。同事的代码也要审，但你可以假设对方大致知道团队禁忌；对 AI，这个假设不成立。它可能优雅地违反你们最在意的那条边界，并且自己写一份看起来很对的理由。

因此流水线设计应遵循：生成 → 自动检查 →（仅绿后）人工审查 → 合并。任何绕过自动检查的快捷通道，都是在用制度鼓励不可信输入直达主干。

## 要点总结：机器查机器，人查判断

1. 生成速度会压垮纯人工审查；可判定问题必须前置给 CI。
2. 类型、lint、测试、扫描各管一类错误，不能互相替代。
3. 把 AI 输出按不可信输入处理：先过滤，再阅读，再合并。
4. 决策边界：机器负责「有没有违例」，人负责「该不该这样设计」——两者抢同一段时间，人会输。
