# 专栏 21 · AI 时代的编程方式

> 所属阶段：S5 全栈、跨端与架构领导力（增值线，可提前穿插）
> 能力增量：从「让 AI 写代码」到「定标准、担责任」
> 计划篇数：30 篇 ｜ 状态：已完结

读者是能独立交付项目的前端工程师。这条线不讲哪个工具更强，只讲一件事：AI 参与到什么程度、由谁划边界、拿什么验收。

这个专栏同时是涨粉主力。写法上的硬要求：

- 每篇落在一个**能独立成立的问题**上，且答案里有明确的判断和取舍，不写成工具使用手册。
- 文末先收束本篇结论，再预告下一篇；不做无信息量的评论区提问。

按大纲分节，节标题用大纲原句，顺序不变。第一条通常是定义，最后一条通常是收束。

## 文章清单

### 模块一：AI 编程到底改变了什么

这一组先把地基铺平：AI 编程是什么、瓶颈移到了哪、什么时候不该用它。给后面所有方法一个判断依据。工具怎么装、提示词怎么写，留在模块二。

- [x] AI编程是什么
  - 发布标题：AI 编程是什么？和普通代码补全的三个区别
  - AI 编程是什么：从补全一行到自主执行一个任务
  - AI 编程和代码补全的三个区别
  - 一次 Agent 任务的生命周期：拆解、执行、检查、迭代
  - 要点总结：AI 编程的边界在哪
- [x] 代码产量不再稀缺
  - 发布标题：代码产量不再稀缺以后，什么变稀缺了
  - 写代码的成本下降之后，瓶颈移到了哪
  - 变稀缺的四样东西：判断、上下文、品味、责任
  - 产出速度和交付速度不是一回事
  - 要点总结：稀缺的是判断力
- [x] vibe coding和工程化的区别
  - 发布标题：vibe coding 和工程化开发的区别是什么
  - vibe coding 是什么，怎么做出来的
  - 什么时候 vibe coding 反而是对的
  - 什么信号说明该从 vibe 切回工程化
  - 要点总结：按任务的风险选流程
- [x] AI改代码的翻车路径
  - 发布标题：AI 改代码改坏了，常见的三种翻车方式
  - 翻车一：顺手把改动范围扩大
  - 翻车二：猜错依赖版本和 API 签名
  - 翻车三：造出重复实现
  - 三种翻车都指向同一个根因：上下文缺失
  - 要点总结：翻车可以追到源头
- [x] 架构师的价值转移
  - 发布标题：AI 能写代码了，架构师的价值转移到哪
  - 从「决定怎么写」到「决定写什么、不写什么」
  - 架构师的三项新职责：定边界、定验收、定弃用
  - 哪些决策必须人来下，不能外包给 AI
  - 要点总结：架构师的产出是一组约束

### 模块二：把需求写成可执行的规格

这一组讲规格驱动。规格是 AI 能读懂的需求，不是给人看的文档。团队的约定、命令、禁区，都落到能判定对错的规则上。跨会话怎么不丢上下文，放在这一组末尾。

- [x] 规格驱动开发是什么
  - 发布标题：SDD 是什么？和写需求文档的区别
  - SDD 的定义：规格是唯一事实来源
  - SDD 和传统需求文档的三个区别
  - 规格、代码、测试三者的关系
  - 要点总结：规格是给 AI 读的需求
- [x] 把需求写成规格
  - 发布标题：怎么把需求写成 AI 能执行的规格
  - 规格的五块：要做什么、不做什么、约束、验收、边界
  - 什么叫可验收：能写成测试的才算
  - 显式写非目标，为什么不能省
  - 要点总结：先写清楚不做的事
- [x] 设计文档锁住方案
  - 发布标题：设计文档怎么写，才能防止 AI 自由发挥
  - 设计文档解决的是选型，不是实现细节
  - 必须写死的三件事：数据模型、模块边界、关键取舍
  - 哪些地方该留白，哪些地方不能留
  - 要点总结：留白越多，跑偏越远
- [x] 任务拆分的粒度
  - 发布标题：任务拆到什么粒度，AI 才不会一次改十个文件
  - 一个任务对应一个可验收的结果
  - 任务拆分的三条硬规则
  - 依赖顺序：先定接口，再写实现
  - 要点总结：粒度决定失控的幅度
- [x] AGENTS.md是什么
  - 发布标题：AGENTS.md 是什么？给 AI 看的项目说明书
  - AGENTS.md 的定义：仓库级的持久上下文
  - 放在哪里，什么时候写
  - 六块内容：项目上下文、命令、目录结构、代码风格、边界、真实示例
  - 和 CLAUDE.md 的分工
  - 要点总结：写给 AI 的入职文档
- [x] 规则怎么写才不啰嗦
  - 发布标题：AI 规则文件怎么写才不啰嗦而且能执行
  - 规则要具体到可判定，不能是抽象描述
  - 抽象描述 vs 真实代码示例
  - 规则写太长会失效，边界在哪
  - 要点总结：能被检查的规则才有用
- [x] 变更流程怎么走
  - 发布标题：OpenSpec 的四步变更流程怎么用
  - 变更流程要解决的核心问题：上下文跨会话丢失
  - propose、apply、sync、archive 各自产出什么
  - archive 为什么是最被低估的一步
  - 要点总结：归档才是知识沉淀

### 模块三：让 AI 拿到对的上下文

这一组讲上下文工程。上下文是预算，不是仓库。工具、规则、喂料方式，三件事各占一篇。Skill 和 MCP 的分工是这一组最常被搞混的地方。

- [x] 上下文窗口是什么
  - 发布标题：上下文窗口是什么？为什么它决定了 AI 的表现
  - 上下文的定义：模型一次能看到的全部信息
  - 为什么长上下文不等于好上下文
  - 上下文被什么挤满：工具定义、历史、文件内容
  - 要点总结：上下文是预算，不是仓库
- [x] 工具定义的上下文成本
  - 发布标题：MCP 工具定义为什么吃掉这么多上下文
  - 工具定义为什么常驻消耗上下文
  - 按需发现和工具搜索怎么缓解
  - 装几个 MCP 服务器才够用
  - 要点总结：少装是最省的办法
- [x] Skill和MCP的区别
  - 发布标题：Skill 和 MCP 有什么区别？一个管知识一个管连接
  - Skill 的定义：可复用的专业知识包
  - MCP 的定义：连接外部系统的开放协议
  - 选型判断：该教方法，还是该连系统
  - 要点总结：Skill 管知识，MCP 管连接
- [x] 渐进式披露
  - 发布标题：渐进式披露是什么？为什么装很多 Skill 也不卡
  - 三层加载：元数据、指令正文、附带资源
  - 为什么只扫元数据这一步很便宜
  - 什么情况下 Skill 会变成 token 负担
  - 要点总结：按需加载的前提是描述写清楚
- [x] Hooks把软约束变硬
  - 发布标题：Hooks 是什么？怎么把 AI 的软约束变成硬拦截
  - Hooks 的定义：生命周期钩子上的确定性脚本
  - 常用的四个触发点各管什么
  - 提示词里的规则为什么会失效，Hook 为什么会生效
  - 要点总结：能自动拦的，别靠说
- [x] 怎么喂对的上下文
  - 发布标题：怎么给 AI 喂对上下文？三个减少浪费的做法
  - 引用具体文件，而不是甩整个仓库
  - 任务做完了就清场，避免旧上下文污染
  - 重要约定落到文件里，不留在对话里
  - 要点总结：会话是易失的，文件是持久的

### 模块四：验收 AI 写的代码

这一组讲质量。AI 生成代码当作不可信输入来审，用自动化检查兜住确定性，用人守住判断。技术债和过期文档是这一组的另一半。

- [x] AI生成的代码怎么审
  - 发布标题：AI 生成的代码怎么审？和审人写的代码有什么不同
  - 当成新人的代码来审：功能对不等于合格
  - 四道关：架构一致、安全、可维护、符合约定
  - 唯一真验收标准：测试
  - 要点总结：看得懂才敢合并
- [x] 为什么必须有自动化检查
  - 发布标题：为什么 AI 写的代码必须过自动化检查
  - 人工审查扛不住生成速度
  - 类型检查、lint、测试、扫描各管什么
  - 把 AI 生成的代码当成不可信输入
  - 要点总结：机器查机器，人查判断
- [x] 测试驱动还成立吗
  - 发布标题：TDD 在 AI 编程里还成立吗
  - 测试先行给 AI 的价值：验收标准变成可执行
  - 让 AI 先写测试，还是后写测试
  - 测试本身也可能被写错，怎么防
  - 要点总结：测试是 AI 唯一能自证的尺子
- [x] 大规模变更怎么审
  - 发布标题：AI 一次改几千行，代码审查怎么做才审得动
  - 变更规模是审查成本的主要来源
  - 拆小变更：把生成量压到一次能读懂
  - 让 AI 少写一点，往往比让人读快一点更划算
  - 要点总结：控制变更的认知体积
- [x] AI生成的技术债
  - 发布标题：AI 生成的技术债长什么样？怎么提前还
  - 重复实现、模块混乱、约定漂移三种典型债
  - 为什么它不会自己暴露：测试还是绿的
  - 定期做一致性检查，不等到烂透再重构
  - 要点总结：技术债在机器速度上累积
- [x] 过期文档的代价
  - 发布标题：AI 读到了过期的 Spec，代码就基于谎言
  - 文档腐化是怎么发生的
  - 文档垃圾回收：高频小规模清理
  - 让 CI 检查代码和规格是否还对得上
  - 要点总结：文档也是要维护的资产

### 模块五：团队规则和人的位置

这一组讲组织层面。什么时候该让 AI 停下，多人怎么并行协作，初级工程师怎么带，效率怎么度量。最后一篇收束到工程师的终局。

- [x] 三次法则
  - 发布标题：同一个问题让 AI 试三次还不行，该怎么办
  - 三次法则的判断依据
  - 卡住通常是规格问题，不是模型问题
  - 人的时间比 token 贵
  - 要点总结：知道什么时候该接手
- [x] 多Agent并行怎么不打架
  - 发布标题：多个 Agent 并行做同一个需求，怎么避免互相打架
  - 分支隔离：每个 Agent 一个工作树
  - 用一个额外的 Agent 做合并裁决
  - 什么时候并行才划算
  - 要点总结：并行省时间，合并要付账
- [x] 初级工程师怎么带
  - 发布标题：AI 时代还要培养初级工程师吗
  - 初级任务变少了，学习路径怎么办
  - 改成评审和调优：新的入门训练
  - 理解成本成了新的瓶颈
  - 要点总结：任务变了，成长没断
- [x] 团队规范怎么定
  - 发布标题：团队 AI 编程规范该写哪几条
  - 规范要落到人、流程、工具三处
  - 必须有的四条：审查、测试、边界、留痕
  - 规范写成文件，还是口头传达
  - 要点总结：规范不写下来等于没有
- [x] 效率怎么衡量
  - 发布标题：怎么衡量 AI 到底带来了多少效率
  - 代码量不是效率指标
  - 三个可看的指标：交付周期、返工率、缺陷密度
  - AI 生成的代码要不要标注来源
  - 要点总结：先有度量，再谈提效
- [x] 工程师的终局
  - 发布标题：AI 之后，前端工程师的终局是什么
  - 会被自动化的部分，和不会被自动化的部分
  - 判断力和品味为什么更贵了
  - 架构能力为什么成了新门槛
  - 要点总结：工程师的终局是决策者
