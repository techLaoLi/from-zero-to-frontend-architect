# 怎么给 AI 喂对上下文？三个减少浪费的做法

**喂对上下文，指的是只把当前任务决策所需的证据放进窗口：具体文件与片段、有效约束、可验证的报错；同时把过期假设和无关整仓噪音排除在外。**

上下文是预算。浪费通常不是「模型太笨」，而是人用整仓、长会话、口头约定三种方式把预算花光。下面三个做法直接对应这三种浪费。

## 引用具体文件，而不是甩整个仓库

模型需要的是证据，不是仓库全息图。

| 做法 | 窗口里发生什么 | 决策质量 |
|---|---|---|
| `@` 相关文件或目录里的明确路径 | 高信号片段进入预算 | 改动边界清晰 |
| 「先把整个项目读一遍」 | 半相关模块、锁文件、生成物抢占位置 | 容易抓错邻居代码 |
| 只给目标、不给入口文件 | 模型自己广搜，路径不可控 | 偶发能做对，成本波动大 |

可执行的默认策略：

1. **先给入口。** 规格、目标文件、失败日志、相关测试，这四类优先。
2. **再按需扩展。** 让 Agent 从入口追依赖，而不是从根目录扫到叶。
3. **拒绝无差别整仓。** 除非任务本身就是仓库级盘点，否则整仓塞入是预算事故。

「多给一点更保险」在短任务里常常反着来：多给的是噪声，挤掉的是你本想强调的约束。

## 任务做完了就清场，避免旧上下文污染

同一会话里的成功，经常变成下一任务的污染源。

污染长这样：上一个需求的「先别动鉴权」、半成品方案、已经否决的库选型，仍作为可见历史留在窗口里。模型没有「你心里已经换题」的同步机制——它只看见还在上下文里的句子。

| 信号 | 建议动作 |
|---|---|
| 目标已变，但还在沿用旧会话 | 新开会话，只带仍有效的文件与结论 |
| 多次试错后历史又长又脏 | 清场；把最终有效结论写进文件再继续 |
| 你开始靠「前面说过」来约束模型 | 说明约束已不在可靠位置，该落盘或重开 |

清场不是丢人，是释放预算。长会话适合同一条任务的连续迭代；不适合当永久工作台。

## 重要约定落到文件里，不留在对话里

对话是易失介质：会摘要、会截断、会新开会话、会换人接手。文件是持久介质：可进 PR、可进 Hook、可进下一轮 `@`。

该落盘的约定包括：

| 约定类型 | 落哪里（示例） |
|---|---|
| 仓库级分工与禁区 | `AGENTS.md`、规则文件 |
| 本次变更的目标与非目标 | 规格 / 变更说明 |
| 验收命令与口径 | 规格或 CI 配置 |
| 已否决的方案 | 设计记录里写明「不采用」 |

口头说「以后都用这种方式」却不落文件，等于把架构决策存在最不可靠的一层。下一会话、下一个 Agent、下一个同事，都可能重新发明一套。

三条做法可以收成一个闭环：**具体引用进窗口 → 任务结束就清场 → 仍要长期生效的写进文件。** 窗口负责当下推理；文件负责跨会话对齐。

## 要点总结：会话是易失的，文件是持久的

1. 引用具体文件和片段，把整仓甩入当成例外，而不是默认。
2. 任务边界一变就清场，避免旧假设继续占用并污染新决策。
3. 重要约定落到 `AGENTS.md`、规格和设计记录，不依赖「前面聊过」。
4. 会话承载当下推理，文件承载长期对齐；预算花在证据上，不花在噪音和怀旧上。
