# AI 读到了过期的 Spec，代码就基于谎言

**过期的 Spec 对 AI 不是「参考旧了」，而是「错误的事实来源」：Agent 会把过期描述当成当前约束去实现，写出能跑、能测绿、却建立在谎言上的代码。**

人读过期文档还会将信将疑；模型默认文档是真的。文档一腐化，生成质量整层塌陷。本文讲腐化怎么发生、怎么用高频小清理做垃圾回收、以及如何让 CI 检查代码与规格是否还对齐。

## 文档腐化是怎么发生的

腐化几乎从不变成一次事故，而是一串「当时来不及改文档」的小决策。

| 触发 | 代码侧发生了什么 | 文档侧常怎么处理 | 对 AI 的后果 |
|---|---|---|---|
| 紧急修线上 | 改了真实行为 | 文档留到下周 | 下周从未到来；Spec 继续描述旧世界 |
| 接口演进 | 字段改名、默认值变化 | 只改了部分示例 | Agent 混用新旧字段 |
| 模块搬迁 | 目录与职责变了 | AGENTS.md / 设计文档未同步 | 新代码写到已废弃路径 |
| 双轨过渡 | 新旧实现并存 | Spec 仍写「唯一做法」 | 生成第二套或调用已死入口 |

人之间还能靠口口相传补洞；Agent 没有那个小道消息频道。它读到的文件就是世界观。世界观错了，规划、实现、甚至它写的测试，都会一起错——而且彼此一致地错，审查时更难一眼看穿。

决策含义：在 AI 工作流里，文档过期从「沟通问题」升级为「正确性风险」。规格、设计决策、AGENTS.md、关键示例，与代码同级，必须进变更流程，不能当wiki随缘更新。

## 文档垃圾回收：高频小规模清理

对抗腐化靠的是垃圾回收，不是年度文档运动。运动式补文档会制造一次性的「看起来很新」，然后迅速再腐化；高频小清理把新鲜度维持在 Agent 可用的水位。

| 做法 | 含义 | 执行要点 |
|---|---|---|
| 变更绑文档 | 改行为的 PR 必须改对应 Spec | 清单化：改了哪条验收、哪段设计、哪个示例 |
| 触碰即更新 | 打开某篇规格做任务时，发现过期就当场改 | 小改直接提交；大改单开「文档对齐」任务 |
| 归档代替堆积 | 过期方案进 archive，不留在现行目录 | 现行目录只放仍有效的事实来源 |
| 删比改更重要 | 不确定还是否正确的段落，删掉或标废弃 | 错误陈述比缺失陈述危害更大 |

优先级按「Agent 会不会读到」排：任务入口会加载的 AGENTS.md、现行 Spec、设计里的数据模型与边界，高于给人看的长篇背景。给人看的叙述可以旧一点；给模型当事实的句子不能旧。

团队要做的决策是分配固定带宽：每个迭代留一小块只还文档债。不留带宽，就等于接受下一轮生成建立在过期事实上。

## 让 CI 检查代码和规格是否还对得上

只靠自觉更新，文档仍然会漂。能自动化的对齐检查，应进 CI；自动化不了的，用抽检和门禁补。

可自动化的对齐例子：

| 检查 | 做什么 | 失败时意味着什么 |
|---|---|---|
| 链接与路径 | Spec 引用的文件、命令、脚本是否仍存在 | 文档指向已删除现实 |
| 契约测试 | OpenAPI / 类型 / 示例请求与实现是否一致 | 接口叙述已撒谎 |
| 验收映射 | 规格中的验收项是否仍有对应测试名或用例 ID | 有句子无尺子 |
| 关键词门禁 | 现行 Spec 目录禁止「临时」「即将废弃」却无日期 | 含糊状态不许充现行事实 |

自动化做不到「这段架构叙述是否仍是团队真意」——那仍要人在设计评审里看。但 CI 可以把「明显对不上」挡在合并前，把人的注意力留给语义。

一条硬门禁值得写进流程：行为变更的 PR，若声称「无文档影响」却改了对外接口或验收语义，审查者直接打回。省几分钟同步，换来的是之后所有 Agent 会话的系统性偏航。

## 要点总结：文档也是要维护的资产

1. 过期 Spec 对 AI 是假事实来源，会生成自洽的错误实现。
2. 用高频小规模垃圾回收维持现行文档，归档旧方案，删除不确定的谎言。
3. 能对上的契约、路径、验收映射尽量交给 CI；语义仍由人审。
4. 决策边界：给 Agent 读的文档与代码同级维护；不维护，就等于给生产线投毒。
