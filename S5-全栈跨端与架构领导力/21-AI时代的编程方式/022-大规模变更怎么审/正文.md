# AI 一次改几千行，代码审查怎么做才审得动

**AI 一次改出几千行时，审查策略的第一刀不是「更快地读」，而是「把变更压回一次能读懂的认知体积」：审不动的 diff，默认不审、不合，先拆。**

人的工作记忆有限，审查质量随 diff 体积下降是物理事实，不是态度问题。本文讲清变更规模为什么主导成本、怎么拆、以及为什么「让 AI 少写」常常比「让人读快」更划算。

## 变更规模是审查成本的主要来源

审查成本的主变量是认知体积：涉及多少文件、多少无关改动混在一起、调用链要在脑子里串多长。行数是代理指标；真正要命的是「读完无法在脑中复述这段变更在干什么」。

| 规模特征 | 审查时发生什么 | 合并风险 |
|---|---|---|
| 单文件、单意图 | 能逐行对规格 | 可控 |
| 多文件、同一意图 | 要跨文件跟踪 | 中等；需按调用链读 |
| 多文件、多意图缠在一起 | 注意力被切碎 | 高；漏审几乎必然 |
| 上千行「顺便重构」 | 审查变成抽样 | 极高；缺陷藏在抽样缝隙里 |

AI 特别容易制造第三、第四类变更：上下文一宽，它就顺手统一命名、提取工具函数、改邻近模块「以求一致」。每一处单独看都像好事，叠在一起就把审查预算烧光。

因此决策规则是：审查队列里的优先级按「能否读懂」排，不按「业务多急」排。读不懂的大包，先退回拆分；用紧急去压审查标准，等于用制度批准漏检。

## 拆小变更：把生成量压到一次能读懂

拆的目标不是制造更多 PR 刷存在感，而是让每一个可合并单元对应一个可叙述的意图。

可执行的拆法：

| 拆法 | 做法 | 验收 |
|---|---|---|
| 按垂直切片 | 一条用户路径或一个接口端到端 | PR 描述能用一句话说完 |
| 按层 | 先接口与类型，再实现，再 UI | 依赖方向单向，可单独合 |
| 先行为后整形 | 行为变更与纯重构分成两次 | 重构 PR 行为测试全绿且无业务 diff |
| 删与加分开 | 删除旧路径和接入新路径不混提 | 回滚时能只回一半 |

给 Agent 的约束要写进任务规格，而不是事后抱怨：

- 一次任务只允许一个意图；发现需要重构，先停，另开任务。
- 默认文件数上限（例如 5 个）和行数上限（例如 300）——超过就拆，除非你书面批准「大爆炸」并指定审查方式。
- 禁止「顺便」：改名、移动文件、依赖升级，各自成单。

「一次能读懂」的操作定义：审查者合上 diff 后，能向第三人复述变更的输入、输出、边界，而不需要再翻文件。复述失败，体积就还太大。

## 让 AI 少写一点，往往比让人读快一点更划算

优化审查有两条路：提高人的阅读吞吐，或降低机器的输出体积。前者有天花板，后者是杠杆。

| 策略 | 成本落在谁 | 效果 |
|---|---|---|
| 训练更快审 diff、用 AI 辅助总结 PR | 人；总结本身会漏 | 边际改善，难改漏检结构 |
| 收紧任务粒度、禁止顺手重构 | Agent 多跑几轮 | 每个 diff 可审，总漏检下降 |
| 生成后先自检再提交人审 | 机器时间 | 人只看已过滤结果 |

决策上应优先选「少写」：

1. **规格里写非目标。** 「不重构邻近模块」「不改公共工具签名」比事后删 diff 便宜。
2. **用测试钉住范围。** 只对目标行为加断言；Agent 改了无关文件导致无关测试红，正好暴露越界。
3. **宁可多轮短任务。** 五次 200 行的可控合并，优于一次 1000 行的赌博。总 token 可能更高，但人的风险时间更低——人时比 token 贵。

「读快一点」的工具可以当辅料：AI 生成的 PR 摘要、风险标注，只用来指路，不能替代阅读关键路径。关键路径仍要人眼过；辅料若写错，会把你带去错误的自信。

## 要点总结：控制变更的认知体积

1. 审查质量首先被变更规模压垮；读不懂的 diff 默认不进入合并流程。
2. 用垂直切片、分层、行为与重构分离，把生成量压到可复述。
3. 优先让 AI 少写、少顺手，而不是逼人审得更快。
4. 决策边界：认知体积是审查的预算单位；超预算就拆，不拿「这次比较急」去透支。
