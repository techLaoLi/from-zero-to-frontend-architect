# 渐进式披露是什么？为什么装很多 Skill 也不卡

**渐进式披露是一种按需加载知识的策略：先让 Agent 只看见很短的元数据（名字与描述），判断相关后再加载指令正文，必要时才打开附带资源。装得多不等于每一次都读得全。**

这就是「Skill 可以很多、上下文却不必然爆炸」的机制前提。本文把三层加载说清，并标出它何时会失效。

## 三层加载：元数据、指令正文、附带资源

把一个 Skill 拆开，通常是三层，而不是一整坨永远进窗口的长文。

| 层级 | 装什么 | 何时进入上下文 |
|---|---|---|
| 元数据 | 名称、一句话/短描述、触发线索 | 扫描阶段，常驻或廉价可见 |
| 指令正文 | 完整步骤、约束、验收口径 | 判定相关后加载 |
| 附带资源 | 模板、长示例、参考文件、脚本 | 执行到需要时再读 |

决策顺序是：先匹配「这是不是这类任务」，再展开「具体怎么做」，最后才碰「大块材料」。和把所有手册第一页就钉在桌上相比，这是在用结构保护预算。

对架构师而言，Skill 设计首先是分层设计：哪一句必须出现在元数据里，哪一段可以留在正文，哪份示例根本不该默认展开。

## 为什么只扫元数据这一步很便宜

元数据的目标是可检索、可判别，不是可执行。

便宜来自三件事：

1. **体积小。** 名字加短描述，通常远小于完整操作手册。
2. **可批量扫描。** Agent 可以在很多 Skill 里做相关度判断，而不必先吞下每一份正文。
3. **错配成本低。** 扫错了，最多是没选中；若一上来就加载全文，错配会直接烧掉大段预算。

因此「装很多 Skill」和「每次会话都很重」不是同一命题。前者描述的是库的规模；后者取决于本轮真正展开了几份正文、又连带读了多少资源。

这也解释了为什么描述质量会变成性能问题：元数据若写得空（「提升效率」「最佳实践」），模型无法靠短信息判别，只能更频繁地误加载正文——便宜层失效，贵的层被反复打开。

## 什么情况下 Skill 会变成 token 负担

渐进式披露不是自动免责声明。下面这些情况会让 Skill 重新变贵：

| 情况 | 为什么变贵 |
|---|---|
| 元数据含糊，正文被频繁误加载 | 扫描省下的预算，在误加载里吐回去 |
| 几乎每个任务都「相关」，正文变相常驻 | 分层名存实亡，等价于常挂长规则 |
| 指令正文本身过长、重复、堆历史 | 一旦加载就很贵；分层只推迟爆炸 |
| 附带资源被默认全读 | 模板和示例当成必读说明书 |
| 与 MCP 工具定义叠加 | Skill 正文 + 庞大工具菜单双开销 |

判断标准很具体：看一次真实任务里，展开了几个 Skill、每个正文多长、有没有顺手读完所有附件。若答案是「经常展开很多、正文很长、附件全开」，那不是「Skill 太多」这么简单，是分层策略没有落到描述和引用纪律上。

治理动作也对应三层：重写元数据让匹配更准；压缩正文只留可判定规则；附件改为显式引用，禁止默认全量。

## 要点总结：按需加载的前提是描述写清楚

1. 渐进式披露把 Skill 分成元数据、指令正文、附带资源，按相关性逐级进入上下文。
2. 只扫元数据便宜，是因为短、可批量判别、错配成本低。
3. 描述含糊、正文过长、附件默认展开、或与厚重工具定义叠加时，Skill 仍会变成 token 负担。
4. 能装很多而不卡，前提不是「系统会魔法压缩」，而是元数据写清楚、正文可判定、资源真按需。
