# 设计文档怎么写，才能防止 AI 自由发挥

**设计文档是规格和实现之间的选型锁：它不写逐行代码，只把数据模型、模块边界、关键取舍写死，让 AI 在允许的方案里实现，而不是自己另开一条架构。**

规格回答「要什么」；设计文档回答「选哪条路」。两者都糊，模型就会同时猜需求和猜架构。本文只处理后一半。

## 设计文档解决的是选型，不是实现细节

设计文档的成功标准不是「写得很全」，而是「关键分叉被关掉」。

模型擅长在局部把代码写圆，不擅长替你承担架构责任。一旦设计层留空，它会按最近读到的文件、训练里的常见模式、当前目录的惯性，选一条看起来能跑的路。这条路常常能跑，也常常和仓库既有结构拧着。

所以设计文档该管的是选型，不该管的是实现细节：

| 该写 | 不该写 |
|---|---|
| 用现有 store 还是新建一个 | 某个函数内部怎么写循环 |
| 数据字段和主键、关联关系 | 每个组件的完整 JSX |
| 模块谁依赖谁、禁止谁依赖谁 | 细到每个文件的伪代码 |
| 为什么不选方案 B | 把教程原文贴进来 |

写到实现细节有两个坏处：一是和代码重复，很快过期；二是挤占注意力，真正该锁的选型反而写虚。设计文档要薄，但薄的是细节，不是决策。

一句话：规格锁目标，设计锁路径，任务锁步子。设计文档越位去写代码，就会既锁不住路径，又妨碍执行。

## 必须写死的三件事：数据模型、模块边界、关键取舍

这三件事一旦放任模型自选，后面的代码审查基本是在救火。

| 必须写死 | 写清什么 | 放任的后果 |
|---|---|---|
| 数据模型 | 实体、字段、来源、持久化位置、校验规则 | 同一概念多个形状，接口和 UI 各猜一套 |
| 模块边界 | 改动落在哪些目录/包，公共 API 是什么 | 跨层调用、循环依赖、重复模块 |
| 关键取舍 | 候选方案、选定项、否决理由 | 下次变更又翻案，架构来回抖 |

**数据模型**要写到「字段级」，不必写到「SQL 级」。前端场景里至少写清：状态放哪、和接口字段怎么对齐、空值和错误怎么表示。模型最爱发明平行结构：你已有 `User`，它再造一个 `AccountInfo`。

**模块边界**要写到「允许依赖」和「禁止依赖」。例如：页面可以调 `features/auth`，但 `features/auth` 不得反向依赖某个页面。边界是审查时最好用的尺子。

**关键取舍**必须带否决理由。只写「我们用方案 A」不够；要写「不选 B，因为会引入新的全局状态，且与现有会话模型重复」。否决理由是给未来的人和未来的 Agent 看的，防止同样的争论再打一遍。

三件事写死之后，实现细节可以留给任务和代码。设计文档的职责到此为止。

## 哪些地方该留白，哪些地方不能留

留白不是偷懒，是把决策权放在对的层级。放错层级，就变成跑偏。

| 层级 | 该不该留白 | 说明 |
|---|---|---|
| 目标与非目标 | 不能留 | 属于规格；留白等于放任范围 |
| 数据模型与模块边界 | 不能留 | 属于设计；留白等于放任架构 |
| 关键库/关键目录选型 | 不能留 | 一次选错，后续全是补丁 |
| 函数命名、局部结构 | 可留白 | 交给实现，用 lint 和示例约束 |
| 具体算法微调 | 可留白 | 有测试兜住即可 |
| UI 文案微调 | 看风险 | 品牌和合规相关不能留；纯展示可留 |

判断口诀：**后果跨多个文件、或多个任务会继承的决策，不能留白；只影响局部且可用测试/lint 兜住的，可以留白。**

常见反例是「先让 AI 出一版设计，我们再改」。可以让它起草，但人必须做选型拍板，并把拍板结果写回设计文档。停留在对话里的设计，下一会话就不存在了。

## 要点总结：留白越多，跑偏越远

1. 设计文档锁的是选型路径，不是实现细节；细节写进设计，既易过期又锁不住架构。
2. 必须写死三件事：数据模型、模块边界、关键取舍（含否决理由）。
3. 跨文件、会被后续任务继承的决策不能留白；局部实现可以留白，用测试和规范兜。
4. 边界在这里：留白越多，模型可搜索的错误路径越多，跑偏越远。
