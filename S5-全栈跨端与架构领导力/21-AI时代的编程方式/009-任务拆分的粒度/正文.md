# 任务拆到什么粒度，AI 才不会一次改十个文件

**任务拆分的目标粒度是：一个任务对应一个可独立验收的结果，改动范围小到人能在一次审查里读完，并且失败时可以单独回滚，而不必拆开十个文件里的缠绕变更。**

规格和设计把「要什么、走哪条路」锁住了。真正翻车常常发生在执行层：一个任务太大，模型一次改开十个文件，审查和回滚一起失效。

## 一个任务对应一个可验收的结果

任务不是「做一会儿的工作量」，而是「交得出证据的交付物」。

可验收意味着：做完后，你能用规格里的某条验收条件，或一条命令、一个行为检查，单独判定这一步过不过。验不了的，就还不是一个任务，只是一段愿望。

| 写法 | 是否合格 | 原因 |
|---|---|---|
| 「把登录相关都做了」 | 否 | 范围不清，无法单独验收 |
| 「给 `AuthSession` 增加 `rememberMe` 字段并写单测」 | 是 | 结果明确，可测 |
| 「重构一下状态管理」 | 否 | 没有结束条件 |
| 「页面接入记住我开关，手动刷新可保持登录」 | 是 | 有可观察行为 |

一个任务只承诺一个结果，不承诺「顺便把周围理顺」。理顺是另一个任务，或者根本不该做。AI 最容易把「相关清理」塞进当前任务；粒度规则就是用来挡住这件事。

验收结果尽量落成：测试绿、类型检查过、或一个明确的手工检查步骤。没有证据，就没有「做完」。

## 任务拆分的三条硬规则

拆任务时，用三条硬规则卡范围。违反任何一条，就继续拆。

| 规则 | 含义 | 反例 |
|---|---|---|
| 单一结果 | 只交付一个可验收结果 | 一个任务里又加功能又做重构 |
| 有限文件面 | 默认只改与结果直接相关的少数文件 | 一次动 API、store、页面、工具函数、文档 |
| 可独立回滚 | 失败或审不过可以整任务丢掉 | 与其他需求的改动缠在同一个 diff |

**关于文件数量：** 「十个文件」不是魔法数字，而是经验红线。跨过它，人通常再也无法在一次 PR 里维持完整心智模型。宁可变两次，也不要一次变到审不动。

**关于重构：** 功能任务里禁止夹带重构。需要重构，先单开任务，先有测试兜底，再动结构。否则出了问题，你分不清是新功能错了，还是重构带崩了。

**关于「小到没意义」：** 拆太碎也会亏——每次冷启动都要重喂上下文。粒度的下限是「结果仍可单独验收」；上限是「diff 仍可一次读完」。落在中间带。

## 依赖顺序：先定接口，再写实现

任务之间有依赖时，顺序错了，后面全是返工。

正确顺序通常是：

1. **定接口或契约**（类型、API shape、模块导出）
2. **写或补齐验收测试**（至少先写失败用例或契约测试）
3. **写实现**
4. **接线到 UI 或调用方**
5. **清理与文档同步**（若需要，单独任务）

| 顺序 | 为什么 |
|---|---|
| 先接口后实现 | 实现可以换，契约不能漂；先锁契约，多 Agent 才不会各写一套 |
| 先测试后接线 | 接线前就有失败信号，避免「页面先通、逻辑后补」的假完成 |
| 调用方最后接 | 上游稳定了再改下游，减少来回改 |

反模式是「先把页面做出来再说」。页面一出来，模型和人都被视觉结果绑架，接口和边界只能事后迁就。看起来快，后面每个任务都在还债。

有并行需求时，更要先定接口。接口是并行的汇合点；没有汇合点，并行就是互相覆盖。

## 要点总结：粒度决定失控的幅度

1. 一个任务只对应一个可验收结果；验不了的不算任务。
2. 三条硬规则：单一结果、有限文件面、可独立回滚；夹带重构直接拆开。
3. 依赖顺序先接口、再测试、再实现、最后接线；顺序反了就会假完成。
4. 边界在这里：粒度决定失控的幅度——任务越大，一次跑偏的半径越大。
