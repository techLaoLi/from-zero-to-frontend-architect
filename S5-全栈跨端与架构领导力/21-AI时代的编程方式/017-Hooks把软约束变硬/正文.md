# Hooks 是什么？怎么把 AI 的软约束变成硬拦截

**Hooks 是挂在 Agent 生命周期上的确定性脚本：在约定触发点自动运行，按规则允许、拒绝或改写下一步，而不依赖模型「是否记得提示词里的那句话」。**

提示词里的规则是软约束，模型可能遵守，也可能在长上下文里淡忘。Hook 把关键红线移出「说服」，放进「拦截」。本文定义机制、四个常见触发点，以及为什么硬拦截更适合当安全网。

## Hooks 的定义：生命周期钩子上的确定性脚本

Hook 的主语是生命周期事件，不是聊天内容。

它和普通规则文件的差别在这里：

| 对比项 | 提示词 / 规则文本 | Hook |
|---|---|---|
| 执行者 | 模型自行权衡是否遵守 | 宿主在事件点强制跑脚本 |
| 结果形态 | 建议、偏好、提醒 | 允许、拒绝、阻断、注入检查结果 |
| 失败模式 | 被忽略、被摘要掉、被冲突规则盖过 | 脚本报错或明确拒绝，路径可观测 |
| 适合什么 | 风格、默认偏好、解释性约束 | 安全、合规、不可逆操作、必跑检查 |

「确定性」指的是：同一事件、同一输入，脚本的判定逻辑是固定的，不靠模型临场发挥。Hook 可以调用你们已有的 lint、密钥扫描、路径白名单，把工程里已经可信的检查接到 Agent 动作前面或后面。

具体产品里的配置字段名会不同；下面按常见 Agent 生命周期描述触发点，名称是示意分类，不是某一家私有 API 的保证。

## 常用的四个触发点各管什么

四个高频触发点，覆盖「开场、动手前、动手后、收尾前」：

| 触发点（示意） | 典型时机 | 主要管什么 |
|---|---|---|
| 会话开始前 | 新会话或任务启动 | 注入环境、校验仓库状态、加载必读约束、拒绝不满足前置条件的开工 |
| 工具调用前 | 读文件、写文件、跑命令、调 MCP 之前 | 拦危险命令、拦越权路径、要求确认、改写参数 |
| 工具调用后 | 工具返回结果之后 | 扫描输出里的敏感信息、失败自动补检查、把关键证据写回会话或日志 |
| 会话 / 提交前 | 结束任务、创建提交、准备交付之前 | 强制测试/类型检查、禁止含密钥的 diff、确认规格与变更清单齐备 |

怎么分工可以记成一句话：**开始前定场地，调用前挡动作，调用后清结果，提交前做放行门禁。**

不是每个团队四个都要上满。优先把「一次做错成本高、且机器能判定」的点做成 Hook；其余仍可用规则文本表达偏好。

## 提示词里的规则为什么会失效，Hook 为什么会生效

软约束失效，通常不是模型「故意对抗」，而是机制上它就可能看不见或权衡掉。

| 失效原因 | 在提示词里 | 在 Hook 里 |
|---|---|---|
| 上下文被挤占或摘要 | 早先的禁令被挤出有效视野 | 事件到了仍执行，不依赖是否还在窗口里 |
| 规则彼此冲突 | 模型挑一个「看起来合理」的解释 | 脚本按你写死的优先级判定 |
| 目标压力过大 | 「先修好再说」压过「别动生产配置」 | 写生产配置的调用在工具前被拒 |
| 需要外部事实 | 模型猜测「应该没密钥」 | 扫描器实际跑一遍再放行 |

所以分工应当是：

1. **能自动判定的红线 → Hook。** 例如禁止删除 `.env`、禁止 `git push --force` 到主分支、提交前必须 `npm test` 通过。
2. **需要品味与权衡的偏好 → 规则文本 / Skill。** 例如命名风格、注释密度、何时抽取组件。
3. **两者都要时，Hook 做门禁，文本做说明。** 说明负责让人与模型理解为什么；门禁负责做错了也过不去。

把安全当提示词优化，是在用概率换确定性。架构上该反过来：确定性检查进 Hook，概率性判断留给人和模型。

## 要点总结：能自动拦的，别靠说

1. Hooks 是生命周期上的确定性脚本，用允许/拒绝/检查来约束 Agent，而不是再写一句「请务必」。
2. 四个常用触发点分别管开工前置、工具前拦截、工具后处理、提交前放行。
3. 提示词规则会因挤占、冲突和目标压力而失效；Hook 在事件点强制执行，不依赖模型是否记得。
4. 能自动判定且做错代价高的约束，优先做成拦截；风格类偏好才留在文本里。
