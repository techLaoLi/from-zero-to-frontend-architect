# vibe coding 和工程化开发的区别是什么

**vibe coding 是一种以对话和即时反馈驱动的开发方式：人靠感觉描述目标，模型快速生成可跑的一版，双方边改边看；工程化开发则先锁规格、边界和验收，再让实现进入可审查、可回滚的流程。**

两者不是道德高低，是风险匹配。本文划清它们怎么做出来的、什么时候 vibe 反而对、什么信号说明该切回工程化。

## vibe coding 是什么，怎么做出来的

vibe coding 的核心不是某个工具，而是工作契约：先出能看的东西，再靠反馈收敛。

典型路径很短：

1. 人用自然语言丢一个大致目标：「做一个能上传头像的设置页」。
2. 模型直接生成页面、接口调用、样式，甚至顺手加几个看起来像样的校验。
3. 人打开看一眼，说「左边不对」「提交后别跳页」，模型再改一轮。
4. 循环到「感觉差不多了」就停，很少先写规格，也很少先锁改动边界。

和工程化对照，差别集中在输入、控制和停手条件上：

| 对比项 | vibe coding | 工程化开发 |
|---|---|---|
| 输入 | 模糊目标 + 现场观感 | 规格、非目标、验收条件 |
| 控制 | 对话里临时改方向 | 变更按边界推进，越界要显式批准 |
| 停手条件 | 「看起来对了」 | 「验收过了，责任人签了」 |
| 产物形态 | 可演示的一版 | 可审查、可回滚的变更 |

vibe 快，是因为它把「写清楚」推迟了。工程化慢在前面，是因为它把不确定提前摊开。两种都在省时间，只是省的位置不同：一个省启动成本，一个省返工和事故成本。

## 什么时候 vibe coding 反而是对的

vibe coding 适合「错了也便宜」的任务。判断标准不是爱不爱用 AI，而是失败代价和信息完整度。

| 适合 vibe 的场景 | 为什么合算 |
|---|---|
| 探索未知交互或视觉方向 | 你还不知道要什么，规格写早了只会锁死错误假设 |
| 一次性脚本、内部工具、演示原型 | 生命周期短，没有长期维护义务 |
| 个人沙盒里验证一个技术猜想 | 错了就删，不影响主线和别人 |
| 需求边界本身还在吵架 | 先做出可讨论的物件，比空讨论文档更便宜 |

这些场景里，工程化流程的前置成本往往高于它能防住的风险。硬走规格 → 设计 → 任务拆分，只会把「还没想清楚」伪装成「已经定了」。

有一条实用边界：如果任务的最坏结果是「浪费几小时」，vibe 通常划算；如果最坏结果是「线上资损、数据错乱、安全漏洞、难回滚的结构变更」，就不该从 vibe 开场。

## 什么信号说明该从 vibe 切回工程化

切换信号出现在产物开始有「留下来的义务」时，而不是出现在「代码行数变多」时。

常见信号：

| 信号 | 它在告诉你什么 |
|---|---|
| 要合进主分支或给真实用户用 | 失败代价从个人时间变成团队责任 |
| 同一段逻辑被改了第三轮还在飘 | 目标没锁，对话在用补丁堆补丁 |
| 开始碰到权限、钱、隐私、多租户 | 默认假设一旦错，后果不可用「再生成一次」抹掉 |
| 需要别人接手或以后还要改 | 没有边界和验收，后续的人只能靠猜 |
| diff 已经大到人审不动 | 产出速度在透支交付速度 |

切回工程化，不是把已有代码扔掉重写，而是补上三件最小设施：

1. **边界**：哪些文件可以动、哪些行为不能变。
2. **验收**：怎样算做完，最好能自动跑。
3. **责任人**：谁有权合并，出了问题谁叫停。

从这一刻起，对话仍然可以用来加速实现，但驱动权要从「感觉」交回「规格和检查」。继续 vibe，等于用更快的速度扩大不确定面。

## 要点总结：按任务的风险选流程

1. vibe coding 靠对话和即时反馈快速出可跑版本；工程化先锁规格、边界和验收，再推进变更。
2. 失败代价低、目标还在探索时，vibe 往往更划算。
3. 一旦要进主线、碰高风险域、需要他人接手，或 diff 已大到审不动，就该切回工程化。
4. 边界在这里：流程不是信仰，是风险匹配；按任务选 vibe 还是工程化，而不是按工具偏好选。
