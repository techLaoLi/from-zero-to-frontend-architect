# Skill 和 MCP 有什么区别？一个管知识一个管连接

**Skill 是可复用的专业知识包：把某类任务该怎么做、注意什么、按什么顺序验收，写成 Agent 能按需加载的说明。MCP 是连接外部系统的开放协议：让 Agent 用标准方式调用编辑器之外的工具、数据源和服务。**

一个管「方法」，一个管「接口」。混用会导致该写进知识包的流程被塞进工具，或该接系统的地方却堆成长提示词。本文给出选型边界。

## Skill 的定义：可复用的专业知识包

Skill 解决的是「这类活，团队已经有固定做法」——不是临时聊出来的一段话，而是可版本化、可分发的知识单元。

典型装进 Skill 的内容：

| 内容类型 | 例子 |
|---|---|
| 方法与步骤 | 发版检查顺序、改设计 token 的流程 |
| 约束与禁区 | 哪些目录不能动、哪些 API 已弃用 |
| 验收口径 | 怎样算做完、要跑哪些命令 |
| 附带材料 | 模板、示例、参考片段（按需再读） |

Skill 的价值在复用：同一套「怎么做前端埋点评审」可以跨会话、跨人、跨仓生效，而不依赖某次对话里有没有人提过。它不替代仓库权限，也不直接变成对外 HTTP 调用；它让模型在做这类任务时先对齐你们的方法。

## MCP 的定义：连接外部系统的开放协议

MCP 解决的是「模型需要碰仓库以外的真实系统」——工单、设计稿、浏览器、内部 API、监控面板等。协议侧约定的是：Agent 如何发现工具、如何按 schema 调用、如何拿回结果。

和 Skill 对照：

| 维度 | Skill | MCP |
|---|---|---|
| 核心交付物 | 知识、流程、约束、示例 | 可调用的工具与资源连接 |
| 主要回答的问题 | 这类任务按什么方法做 | 去哪个系统读/写什么 |
| 失败形态 | 方法过期、描述含糊、选错 Skill | 鉴权失败、接口变更、工具过多挤占上下文 |
| 是否必须联网/接服务 | 通常不必 | 常常要 |

MCP 让 Agent 具备「手」去碰外部世界；Skill 让 Agent 具备「这个团队的手艺」。没有 MCP，很多集成只能靠人在对话框里粘贴；没有 Skill，每次都要把方法从头说一遍，而且说法还容易漂。

## 选型判断：该教方法，还是该连系统

用一件具体任务来拍板，不要先问「哪个更先进」。

| 你的真实缺口 | 该选什么 | 反例 |
|---|---|---|
| 团队有固定流程，但模型每次做法都不一样 | Skill | 为流程单独做一个「口头提醒」MCP |
| 模型需要读 Figma / 工单 / 线上日志才能继续 | MCP | 把整页接口文档粘进 Skill 冒充连接 |
| 既要标准流程，又要打外部系统 | Skill + MCP，分工写清 | 把流程步骤硬编码进某个工具的描述里且无处可查 |
| 只是本仓读写和跑测试 | 先用内置能力，两者都可以不装 | 为「显得完整」预装一堆 |

两条快速规则：

1. **教方法 → Skill。** 内容是判断、顺序、禁区、验收；改的是文档和示例，不是服务端点。
2. **连系统 → MCP。** 内容是鉴权后的读写真操作；改的是连接与权限，不是散文式说明。

若一项能力两边都能勉强塞，优先问：它需要实时状态吗？需要写副作用吗？需要权限边界吗？三个里有「是」，偏 MCP；三个都是「否」，且重点是可复述的方法，偏 Skill。

## 要点总结：Skill 管知识，MCP 管连接

1. Skill 是可复用的专业知识包，对齐方法、约束和验收。
2. MCP 是连接外部系统的协议，对齐工具调用与数据进出。
3. 选型看缺口：方法不稳定用 Skill，系统够不着用 MCP；两者可并存，但职责不要糊成一团。
4. 架构决策是分工，不是堆叠：该沉淀的进知识包，该集成的走连接，避免用提示词同时冒充两者。
