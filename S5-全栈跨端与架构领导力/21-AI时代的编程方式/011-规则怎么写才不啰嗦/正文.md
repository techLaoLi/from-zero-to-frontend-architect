# AI 规则文件怎么写才不啰嗦而且能执行

**能执行的 AI 规则，是具体到可以判定对错的约束：写清允许什么、禁止什么、例外是什么；最好附真实代码示例，并能被 lint、测试、审查或钩子检查——只写抽象口号的规则，等于没写。**

`AGENTS.md` 和各类规则文件解决的是「长期约定怎么进入模型上下文」。约定写虚了，模型会点头；写长了，模型会漏看。本文处理这两端的失败模式。

## 规则要具体到可判定，不能是抽象描述

规则的验收标准只有一个：第三人拿到一段 diff，能判定它有没有违反。

「注意代码质量」「保持可维护」「遵循最佳实践」都不可判定。它们是态度，不是规则。模型无法对态度闭环，审查也无法对态度打回。

把抽象句改成可判定句：

| 抽象描述 | 可判定规则 |
|---|---|
| 保持组件简洁 | 单个组件文件不超过 200 行；超过就拆 |
| 注意安全 | 禁止把密钥写进仓库；密钥只从环境变量读 |
| 别乱加依赖 | 新增生产依赖必须先改规格并说明理由 |
| 风格统一 | 使用项目 ESLint；禁止关闭已有规则来过关 |

可判定规则通常具备三要素：**对象、动作、边界**。对象是什么文件/场景；动作是必须或禁止；边界是例外是否允许。缺任何一项，执行时就会抬杠。

写规则时先问：违反它时，我能指出具体哪一行吗？指不出，就还没写完。

## 抽象描述 vs 真实代码示例

同一条规则，口号版和示例版对模型的约束力差一个数量级。

口号版：

```text
不要在组件里直接请求网络，把请求放到统一的数据层。
```

示例版：

```text
页面和组件禁止直接调用 fetch/axios。
通过 `src/features/<name>/api.ts` 导出的函数取数。

✅ 允许：
const users = await listUsers()

❌ 禁止：
const res = await fetch('/api/users')
```

对比关系可以压成一张表：

| 写法 | 模型通常怎么理解 | 审查成本 |
|---|---|---|
| 抽象口号 | 自行发明「差不多」的结构 | 高，需要争论 |
| 禁止项 + 允许项 | 搜索空间被切开 | 低，对号入座 |
| 禁止项 + 允许项 + 短示例 | 按样例模仿 | 最低 |

示例要短，只保留对比信号。不要贴一整页生产代码。示例过长，规则文件本身又变成噪音。

一条经验：凡是团队已经为它吵过两次的约定，都值得写成「禁止 / 允许 / 示例」三段，而不是再写一句形容词。

## 规则写太长会失效，边界在哪

规则不是越多越安全。上下文是预算；规则文件也在花这笔预算。

写太长的典型后果：

1. **关键约束被淹没**，模型记住了次要句，漏了禁区。
2. **与任务提示冲突时更难裁决**，因为到处都是「也很重要」。
3. **维护成本上升**，过期规则删不干净，反而提供错误指导。

长度边界用「可执行密度」衡量，不靠字数迷信。一份规则文件建议守住：

| 检查项 | 建议 |
|---|---|
| 总长度 | 控制在一次能扫完；宁可拆文件，也不要堆成说明书小说 |
| 单条规则 | 一句话能说清判定；细节用短示例，不写小作文 |
| 重复 | 已有 lint/test 能拦的，不要再在规则里散文重复 |
| 优先级 | 安全与破坏性操作 > 架构边界 > 风格偏好 |
| 更新 | 三个月没被引用或检查过的规则，删或合并 |

拆分策略：仓库级通用规则放 `AGENTS.md`；高成本流程写成按需加载的 Skill；可用脚本强制的，交给 Hooks 或 CI。规则文件只保留「必须进模型上下文、又不能完全自动化」的那一层。

一句话：规则的敌人不是短，是不可判定；也不是长，是没有优先级的长。

## 要点总结：能被检查的规则才有用

1. 规则必须具体到可判定：对象、动作、边界齐全；抽象口号无效。
2. 真实示例（允许/禁止对照）比形容词更能约束模型，也更能降低审查成本。
3. 规则过长会失效；按优先级裁剪，能自动化的不要重复写进散文。
4. 边界在这里：能被检查的规则才有用——人能判定，或机器能拦住。
